## Problem statements (build in at least one)

**The System That Gets Better.** Build an autonomous coding system that completes a hard, tightly coupled software task and improves itself as it works. Each failure becomes a versioned change to its skills, tools, routing or context, and each change has to prove itself on held-out work. How can it keep making progress over a long task, adopt only the changes that held-out evaluation confirms, and roll back the rest?

**Software Archaeology.** Recover, rebuild, port or extend authorized software from incomplete evidence such as binaries, runtime traces, partial code or documentation. Ship behavioral evidence that separates what was observed from what was inferred. How can a system map an unfamiliar program, track its uncertain hypotheses, and prove behavioral equivalence across platforms, languages or runtimes?

**Trust but Verify.** AI writes code faster than teams can check whether it's safe to merge. Build an independent verifier that evaluates AI-generated changes, catches defects, and blocks or rolls back anything below the required standard. How can a verifier write its own tests without sharing the implementer's blind spots, and stay independent, reproducible and hard to game?

## Rules

- Open source: repositories must be public.
- Team size: at most four.
- Demo requirements: your demo must only highlight the specific features, code and functionality that your team built during the hackathon. Judges must be able to clearly identify what was created during the event. Failure to clearly identify your original contributions will result in immediate disqualification.
- New work only: you may not present an existing project as your own work. Failure to clearly distinguish your contributions will result in immediate disqualification.
- Banned projects: projects that violate legal, ethical or platform policies, or use code, data or assets you do not have the rights to.
- Anti-projects (strictly no), among them: basic RAG apps, Streamlit apps, image analyzers, education chatbots, and **any project where a dashboard is the main feature**.

## Submission

Submit on the Cerebral Valley form when hacking is done. It requires a **short one-minute demo video** highlighting the specific features, code and functionality the team built during the hackathon. Check that the repository is public, the demo link is accessible, and all team members are added to the submission page.

## Judging

Round one: judging groups in separate rooms; about **3 minutes of live demo** plus 1 to 2 minutes of Q&A.

| Criterion | Weight | The guide's question |
|---|---|---|
| Technical Demo | 35% | How is the actual demo of the project? Does it impress you? Is it well-engineered and working? |
| Implementation Difficulty | 30% | How hard is this project to recreate? Is the technical depth more than a few AI prompts away? |
| Impact Potential | 20% | Does the project address a significant real-world issue or pain point? |
| Creativity | 15% | How creative is the project? Is this something you have never seen before? |

Round two: the top six demo on stage (about 3 minutes plus 1 to 2 minutes of Q&A), same criteria, equal weights.
